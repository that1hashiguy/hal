WHY IT MATTERS

What does a user gain?

The visible app remains a simple HTML page. The value is in making the connection’s identity, key exchange, and compatibility visible and testable before a team changes production traffic.

FOR A BROWSER VISITOR

A connection they can inspect

The visitor sees the same page and can inspect the certificate chain. Where the client supports the mode and trusts its private root, hybrid key exchange adds a post-quantum component that can help protect recorded traffic against a future break of the classical exchange, provided ML-KEM and the negotiated handshake remain secure. The PQC certificate mode also exercises post-quantum server authentication.

FOR A SERVICE CONSUMER

Verified service-to-service identity

In the workload demo, the frontend checks the backend before forwarding the request and the backend accepts only verified clients. The browser can keep using conventional HTTPS while the private hop exercises ML-DSA mTLS and hybrid key exchange.

FOR A TEAM PLANNING MIGRATION

A way to stage change

Separate listeners reveal whether a failure comes from a certificate algorithm, a key exchange group, trust configuration, or the client. The local measurements and evidence help choose the next compatibility test; they are not a production performance forecast.

TERMS / 01

1. Terms in the guide

A few terms carry different meanings in different layers. These definitions describe how HAL uses them here.

Post-quantum cryptography (PQC)
Algorithms designed to resist attacks by future large quantum computers. This guide uses ML-DSA for signatures and ML-KEM for key establishment.
Crypto agility
The ability to change cryptographic choices and verify the result. In this lab, four NGINX listeners isolate combinations of server certificate and TLS key exchange group.
TLS hop
One connection between two peers. Browser → NGINX and frontend → backend are separate hops, with separate handshakes and evidence.
Service and NodePort
Kubernetes routing objects. For example, the host’s port 8096 maps through a KinD NodePort and Service to the agility NGINX pod’s 8445 listener; “Service” does not mean a second backend application.
Frontend and backend
The two pods in the --pqc workload lab. The agility page on 8094–8097 is a different, single-pod app and does not forward to that backend.
Root, intermediate, leaf
The root is the trust anchor; the intermediate is the issuing CA; the leaf identifies the server or client. A peer checks the presented leaf and intermediate against a root it already trusts.
ML-DSA-65
A post-quantum digital signature parameter set. Here it signs PQC CA and leaf certificates and authenticates peers during the TLS handshake.
ML-KEM-768
A post-quantum key encapsulation parameter set used to help establish shared session keys. It is not a certificate signature algorithm.
Hybrid X25519MLKEM768
A TLS 1.3 key exchange group combining X25519 and ML-KEM-768. It is distinct from standalone MLKEM768.
Mutual TLS (mTLS)
Both peers present and verify certificates. In the workload lab, the frontend verifies the backend server identity and the backend verifies the frontend client identity.
Private trust
The HAL CA roots are not installed as public browser roots. A browser user must explicitly trust the intended root before interpreting a successful browser certificate check.
Evidence
Observed facts tied to a connection, such as the negotiated group or a verified peer certificate. A configured value describes policy; it does not by itself prove what a browser negotiated.

ARCHITECTURE / TWO TLS DECISIONS

Identity is one decision.
Key exchange is another.

A TLS connection answers two different questions. The certificate and handshake signature authenticate an endpoint. The negotiated group establishes shared session keys. ML-DSA-65 is a signature algorithm for identity; ML-KEM-768 is a key encapsulation mechanism used for key establishment. One can change without the other.

01 / AUTHENTICATION

Who am I talking to?

Build a leaf → intermediate → trusted root chain, check the DNS name and certificate purpose, then verify the endpoint’s handshake signature.

Here: RSA or ML-DSA-65
02 / KEY ESTABLISHMENT

How are session keys made?

The TLS peers negotiate a group. Hybrid X25519MLKEM768 combines a classical exchange with ML-KEM-768; the pure mode requires standalone MLKEM768.

Here: X25519, hybrid, or MLKEM768

Vault’s boundary: it issues identities. NGINX/OpenSSL negotiates key exchange and protects traffic. Vault does not distribute the TLS session keys.

Why four ports?

The tested NGINX image applied the default listener’s group policy across SNI names that shared a port. HAL gives every mode its own listener and Service port, and uses fresh connections so a previous mode’s TLS session does not blur the comparison. On an older KinD cluster without the host mappings, a local port-forward reaches the same Service directly.

PATTERNS / PRIVATE WORKLOAD HOP

The fifth pattern: private mTLS

The separate --pqc workload lab has its own frontend page at pqc.localhost:8093. Frontend NGINX terminates that browser connection using a self-signed ECDSA P-256 certificate. Clicking Test connection makes this frontend proxy a request to a distinct backend NGINX pod over TLS 1.3 with mutual ML-DSA-65 authentication and hybrid X25519MLKEM768 key exchange.

  1. 01

    Provision identities

    Vault’s hal-pqc-root signs hal-pqc-int. Separate issuance roles create a clientAuth-only frontend leaf and a serverAuth-only backend leaf. Both pods trust the PQC root.

  2. 02

    Verify each other

    The frontend checks the backend’s chain and full Kubernetes Service DNS name. The backend checks the frontend’s client chain and explicit clientAuth purpose. Both peers prove their ML-DSA keys during the handshake.

  3. 03

    Establish keys and send data

    The same handshake negotiates X25519MLKEM768. TLS then protects the forwarded request and response with symmetric session keys. Vault is not on this data path.

  4. 04

    Rotate without a pod restart

    Each workload uses a scoped Vault token to request a fresh leaf at about half its remaining lifetime. The default leaf TTL is 10 seconds. NGINX/njs swaps identities for new handshakes.

Trust boundary: the workload CA is private and distinct from the browser’s ECDSA identity. Vault administrators and readers of the workload issuance-token Secrets can impersonate the workloads. This lab does not add application authorization or revocation checking.
PATTERNS / TRY THE LAB

Run the paths in order

The agility app reuses both existing CA hierarchies. Bring up conventional PKI first, then the PQC workload lab, then the browser comparison. These commands change local Vault and KinD state; this guide itself is static.

hal vault pki enable
hal vault pki enable --pqc
hal vault pki enable --agility
hal vault pki status --agility

HAL writes the browser roots to ~/.hal/crypto-agility/traditional-root.pem and pqc-root.pem. Compare their SHA-256 fingerprints, then explicitly trust only the root needed for the mode you test. In Chrome, use chrome://certificate-manager for local certificates. Inspect the leaf, DNS SAN, issuer, and chain in the browser’s certificate viewer. Remove the imported roots when finished; disabling HAL’s lab does not remove browser trust.

For the experimental Pure PQC listener, use OpenSSL 3.5+ with the PQC root and the standalone group:

openssl s_client -connect 127.0.0.1:8097 -servername pure.agility.localhost -tls1_3 -groups MLKEM768 -verify_return_error -verify_hostname pure.agility.localhost -CAfile ~/.hal/crypto-agility/pqc-root.pem -brief </dev/null

What to observe

  1. Traditional and Hybrid: inspect the same RSA trust chain in the browser, then compare the server-observed X25519 and X25519MLKEM768 groups in each page’s diagnostics.
  2. Hybrid + PQC certificate: inspect the ML-DSA-65 leaf and private PQC chain in a compatible browser, alongside the server-observed hybrid group. A page load alone does not show the browser’s trust verdict to JavaScript.
  3. Pure PQC: use the guide’s OpenSSL command with the PQC root and required MLKEM768 group. A default browser failure may happen before HTML or diagnostics can load.
  4. Private mTLS: open the separate 8093 workload page and run Test connection. Confirm frontend chain/DNS verification, backend client-certificate verification, both ML-DSA handshake signatures, and the negotiated hybrid group in that test’s evidence.

COMMON THREAD / 04

4. Similarities among the patterns

All five patterns make the same TLS decisions in the same order. The algorithms, peers, and trust anchors change; the questions each peer must answer do not.

01

Obtain an identity

Vault issues the four agility server leaves and both workload leaves under separate roles. The workload page’s browser-facing ECDSA certificate is the exception: HAL creates it locally for that separate browser hop.

02

Present and verify it

NGINX presents a certificate and proof of its private key. The peer checks a chain to an explicitly trusted root and the certificate purpose. A client also checks the server’s DNS name; on the workload hop the backend checks the frontend’s clientAuth purpose.

03

Negotiate session keys

NGINX/OpenSSL applies the listener’s TLS policy. The certificate algorithm does not choose the key exchange group: the peer must offer a compatible group, whether X25519, hybrid X25519MLKEM768, or standalone MLKEM768.

04

Exchange data and inspect this hop

Once TLS completes, application data travels over that connection. The server can report its observed TLS parameters; the browser decides whether it trusted its own connection. The workload test gathers separate backend-side evidence for the private hop.

The migration lesson: changing the certificate, key exchange, or trust root independently lets a team locate compatibility problems before combining changes. The five patterns are examples of those choices, not a universal rollout sequence.

UNANSWERED / 05

5. Open questions

This guide shows the HAL lab’s design and evidence. A production decision needs answers from the clients, networks, policies, and operations of the environment that will use it.

CLIENT COVERAGE

Which actual clients can connect?

Test the browser, OS, TLS library, proxy, and device versions your users have. Record certificate validation and negotiated groups separately for each hop.

TRUST DISTRIBUTION

Who installs and removes the roots?

Decide how private roots reach managed browsers and workloads, how fingerprints are verified, and how trust is withdrawn after the lab or a CA rotation.

FAILURE POLICY

What happens when a client lacks the required group?

Define whether the service refuses the connection, offers an explicitly chosen fallback endpoint, or routes the client elsewhere. Measure whether that behavior matches the security policy.

OPERATIONS

Can issuance and rotation meet real uptime needs?

Test Vault outages, token renewal, certificate expiry, monitoring, and recovery at realistic lifetimes and request rates. The ten-second workload TTL is a demonstration setting.

AUTHORIZATION

What may an authenticated workload do?

mTLS establishes a peer identity. Define a separate application policy that maps that identity to allowed operations and test how it is enforced.

MEASUREMENT

What is the cost on real networks?

Compare handshake success, certificate-chain bytes, latency, CPU, and user-visible loading across representative clients. The local browser and OpenSSL benchmarks are starting points.

SUPPORT & EVIDENCE / 06

6. Limits

A browser error, a loaded page, and a successful workload test answer different questions. Keep the result tied to the hop that produced it.

01

Chrome and private ML-DSA

Chrome 150+ documents ML-DSA TLS certificates in private PKI when the root is explicitly trusted. That does not make these leaves publicly trusted. The browser must still validate the exact hostname and chain.

Chrome private PKI support ↗
02

Firefox and ML-DSA certificates

In the repo’s observed Firefox session, Hybrid loaded but Hybrid + PQC certificate failed. That points to certificate authentication or trust, but the browser error alone does not prove the exact cause. Firefox/NSS support is evolving; check the build you test.

Mozilla ML-DSA tracking ↗
03

Hybrid is not standalone ML-KEM

Chromium’s default TLS group list includes X25519MLKEM768, but not standalone MLKEM768. The Pure PQC listener therefore likely fails before the page loads in default Chrome. Use an OpenSSL 3.5+ client to verify that listener.

Chromium group defaults ↗
04

What the page can observe

JavaScript cannot inspect the browser’s trust verdict or a TLS handshake that failed before loading. The agility page shows configured certificate data and server-observed TLS facts. The workload test reports backend observations for its own mTLS connection.

HAL evidence semantics ↗
05

Issuance and revocation

HAL uses Vault’s direct PKI API for ML-DSA issuance and short-lived workload leaves. Vault documents that ML-DSA cannot currently be used with its ACME issuance protocol or OCSP. The workload lab does not implement separate revocation checking.

Vault PKI considerations ↗
06

Lab scope and performance

Private roots, loopback KinD ports, a ten-second default workload TTL, and local timing samples make this a compatibility lab. Its results do not establish public browser trust, application authorization, or production latency.
